# atk 维护手册

> 框架会死于没人维护，而不是死于技术（规范第 13 章）。
> 本文规定角色、节奏、阈值调整流程、Judge 校准流程、灰度与回滚、回流 SLA，
> 以及必须监控的「框架自身」三个指标。

---

## 1. 角色与时间投入

| 角色 | 职责 | 建议投入 | 本仓库默认责任人 |
|---|---|---|---|
| 测试负责人 | 定 rubric、门禁阈值、裁决争议、发布签字 | 0.5 FTE | 张三 |
| 用例维护人 | 用例增删改、换血、Flaky 复核、`expect` 语义质量 | 0.3 FTE | 李四 |
| Judge 维护人 | 校准集维护、偏差诊断、判官版本回归 | 0.2 FTE | 王五 |
| 场景 Owner | 各业务线提供黄金用例与验收口径 | 各 0.1 FTE | 订单/文档/安全等 |

**只有 `expect` 的语义有人长期负责，指标才长期可信。** 其余都可以自动化。

---

## 2. 固定节奏

| 周期 | 动作 | 产出 |
|---|---|---|
| 每周一 | 消化 bad case 回流（≥3 条进黄金集） | 用例 PR |
| 每周五 | 复核隔离区（`atk quarantine list`），确认是环境抖动还是产品缺陷 | 复核记录 |
| 每两周 | 门禁阈值复盘：是否过严导致绕过、过松导致漏放 | 阈值调整 PR |
| 每月 | 评估集换血 20%、Judge 重校准、红队补新样本 | 新数据集版本 |
| 每季 | 框架自评（成熟度、指标有效性、ROI） | 自检报告 |

## 3. 门禁阈值调整流程

1. 看板/报告里出现「显著退化」或「长期不显著退化」；
2. 先判断是不是**环境/数据**问题（报告「归因分布」第一行）；
3. 确认是产品退化后，按维度调整 `config/atk.yaml` 的 `thresholds.dims`；
4. 调整必须写清理由与生效日期（PR 描述里写）；
5. 调整后跑一次 `atk selfcheck`，确保没有把框架自己搞坏。

**禁止**为了「让版本过」而整体放宽阈值。正确做法是逐维度、带理由地调。

## 4. Judge 校准流程（每次改 Judge Prompt / 换 Judge 模型都要重跑）

```bash
# 1) 跑校准集，得到 Kappa、混淆矩阵、长度/位置偏差、反向红队被骗率
atk calibrate --judge openai:judge-v2 --base-url $JUDGE_URL --set cases/calibration --strict

# 2) 看三个硬指标
#    - 总体 Kappa ≥ 0.6（≥0.8 良好）
#    - 反向红队被骗率 ≤ 15%
#    - 不存在明显长度偏差（|Spearman| ≤ 0.3）
# 3) 任一不达标 → 该 Judge 不得用于门禁，只能作为参考分
```

校准集要求：

- 与评估集**物理隔离**（`cases/calibration` vs `cases/golden`）；
- ≥20 条（推荐 50~100），其中反向红队样本 ≥5 条；
- 覆盖四类失败模式：编造数字、谎报完成、交付缺失、过度拒答。

## 5. Flaky 隔离区

```bash
atk quarantine list
atk quarantine add --case-id AGT-XXX-0001 --reason "三轮结果不一致"
atk quarantine remove --case-id AGT-XXX-0001 --reason "确认是环境抖动，已修复"
```

规则：

1. 同版本同用例连续 3 轮结果不一致 → 自动进隔离区；
2. 隔离区用例**不计入门禁分子分母**；
3. 每周人工复核：若是模型本身不稳定，按**真实产品缺陷**修复，不要长期隔离；
4. 隔离超过 4 周未处理，自检报告会提示。

## 6. 灰度阶梯与回滚条件

| 阶段 | 流量 | 进入条件 | 回滚条件 |
|---|---|---|---|
| 离线评估 | - | 门禁 PASS | 门禁 BLOCK |
| 影子模式 | 同流量双跑，不对外 | 离线全维度通过 | 影子结果与线上差异 >5pp |
| Canary 1% | 1% | 影子对比无显著退化 | 任务完成率下降 >2pp 或出现安全事件 |
| Canary 5% | 5% | 1% 观察 24h 无异常 | 同上 |
| 全量 | 100% | 5% 观察 48h 无异常 | 任意安全事件立即全量回滚 |

**回滚决策必须基于分维度指标，不能只看总分。** 安全维度出现任意失败即回滚。

---

## 7. bad case 回流 SLA

- 用户差评 / 人工接管的 case：**48h 内**进入待标池；
- 每周固定消化 **≥3 条**进黄金集（含期望值与黑名单）；
- 回流用例必须标注来源 `meta.source: online`、责任人与换血日期；
- 未按期消化的，自检报告第 10 项会告警。

---

## 8. 必须监控「框架自身」的三个指标

| 指标 | 定义 | 健康阈值 | 怎么算 |
|---|---|---|---|
| 门禁**误拦率** | 被拦但线上实际没问题 | <10% | 发布后 7 天回溯被拦版本的线上事故数 |
| 门禁**漏放率** | 放行但线上出事 | <5% | 线上事故中门禁判 PASS 的比例 |
| 团队**绕过率** | 绕过门禁发版的次数占比 | <20% | 发布记录里 `--no-gate` / 手工改阈值次数 |

> 绕过率超过 20%，说明框架设计有问题（太慢/误杀太多），而不是团队纪律问题。
> 这时应该做影响面分析、拆分档位，而不是加强审批。

## 9. 常见问题

**Q：报告说「未覆盖维度」怎么办？**
A：说明该维度没有任何断言覆盖。去补 `grade.auto_checks` 或 `expect.must_achieve` 的维度，别用总分掩盖。

**Q：门禁一直 WARN 但不 BLOCK？**
A：样本不足导致的「不显著退化」。按报告里的 MDE 估算扩容，或接受告警继续灰度。

**Q：能改 `expect` 让用例通过吗？**
A：只能改「错误的期望」（误杀合法解），不能改「产品的问题」。每次修改期望必须在 PR 里说明理由，并由测试负责人 review。

**Q：录制的 baseline 过了 100%，是不是太理想？**
A：演示录制是「参考轨迹」，用于验证链路；真实接入用 `--agent http:<url>`。框架自测（`tests/`）用人工构造的轨迹独立验证断言，不依赖录制。
